Payment workflow update · October 22, 2026

Payment operations: presenter and navigation reference

Aligned to docuflow-tax-assessment-reviewed(2).html, including its Payment module and fresh seeded dataset. Tax guidance is retained below. Payment data uses a separate browser storage record; switching personas shares the same cases and changes available work and actions.

Demonstration boundary: HIVE acknowledgments, OBS capture and release are simulated. Browser persona checks are not production authorization. “Completed / Archived” means a simulated release was recorded; it does not assert settlement.

Prepare the demonstration

  1. Open the exact prototype named above in a separate tab. In the Tax workspace, select Payments in the sidebar or Open payments → on the landing page/process library. Entry selects Emma Laurent.
  2. Before rehearsal, choose Scope & decisions → Reset payment demo data and confirm. This clears Payment demo edits/history and in-session attachments, while retaining Tax data. Never reset in the middle of a presentation without explaining it.
  3. Use Payment overview and search by the full case ID. Click the fund name in the matching row to open it. The ID itself is displayed under the name.
  4. Select the named persona using the top persona dropdown. Switching Payment personas keeps the open case; available actions change. Changing a role with an unsaved instruction may prompt to discard edits.
  5. Claim each required task. Team queue contains eligible unclaimed work; My tasks contains claimed work. A fresh My tasks queue can correctly be empty.

Timing: 20–25 minutes for the core sequence; add 5–10 minutes for draft, return and supervisor alternatives. Case counts and stages below apply immediately after Payment reset.

Additional flows

Draft → CSM validation → parallel controls

Emma Laurent → Payment overview → PAY-2026-2008 → Overview → Edit instruction. Keep PPMP and two lines. Use fictional sample instruction if needed. Review the demo scope/first-call/release inputs; choose Save draft or Submit to CSM validation. Submission opens Documents. Check both signature and authority confirmations, enter rationale and select Validate & start parallel controls. L1 has changed banking information, so the demo requires a new callback. This is a separate rehearsal; it is not part of the P1–P9 case.

For a new case, choose + New payment. PPMP requires at least two lines; PPSP requires exactly one. IDs are allocated from saved state, so search using the returned ID rather than promising PAY-2026-2009.

Return, recovery and terminal RED are different

An Unsuccessful payment callback moves the case to Returned to CSM. A CSM can edit and resubmit; the demo clears prior control results and capture. A checker/supervisor can choose Return to maker with a comment; this returns to Capture. Depositary Red creates recovery work. Red on PERE Ops assessment, investment callback or recovery immediately sets Stopped / Archived in the current code and records CSM notification. There is no separate CSM acknowledgment task before this terminal transition.

Empty queues or unavailable actions

Check persona → case stage → task claim → case tab. Search Payment overview when a case is absent from Team queue. Use Completed / Archived for completed records. Fresh My tasks is empty because no tasks are claimed. PAY-2026-2006 deliberately has no actionable callback while on policy hold. Do not reset to fix an expected role/stage restriction.

Questions before implementation

  • Approve callback threshold/boundary, FX source/as-of/rounding, and precedence of prior callback reuse versus amount and changed banking data.
  • Approve PERE scope/first-call source and handling of stale or unavailable indicators.
  • Decide PERE case-versus-line coverage, partial PPMP release and supervisor routing/aggregation.
  • Confirm when RED is recoverable, who acknowledges it, and whether stopping and archival are separate actions.
  • Approve real group IDs, task eligibility, canonical-person maker/checker rules, delegation and reassignment.
  • Confirm evidence matching, signed instruction/version rules, authoritative OBS confirmation, reconciliation and duplicate handling.
  • Define retention, legal holds, restart policy, SLAs and audit/access controls.

8 · Inline requirements and coverage register

Use these anchors while walking through the execution paths. “Demonstrated” always means local prototype behavior, not production compliance.

R01 · One document identity and retained history

Requirement: Each upload has a persistent ID; link account/partner context and preserve replacement lineage.

Prototype evidence: Demonstrated locally through document IDs, hierarchy display and linked records. Dashboard evidence summaries count unique document IDs in scope and distinguish code, ownership and subtype where available.

Before implementation: Confirm identity versus revision model, umbrella/mandate/portfolio relationships, repository and binary ownership.

R02 · Controlled document intake

Requirement: Document Format, type and ownership constrain who may upload and through which channel.

Prototype evidence: Partial role/format and inventory checks; paper custody field; three intake specimens.

Before implementation: Approve full role/channel/format/signature matrix and PDF/A/seal-preservation controls.

R03 · Automatic embedded workflow

Requirement: Eligible document context starts verification without a manual workflow choice.

Prototype evidence: Uploads/scans create Processing records for the shared check queue.

Before implementation: Specify executable routing and rules per type/owner/subtype and deploy actual engine models.

R04 · Document validation and separate review

Requirement: Verify quality, metadata, ownership and applicable signatures; preserve originals.

Prototype evidence: Complete/Incomplete/Rejected outcomes; comments; multipage specimens and review notes.

Before implementation: Define acceptance criteria, legally effective signing, PDF/Office editing, page integrity and approved viewer services.

R05 · Clear work ownership

Requirement: Users see tasks, drafts, returns, blockers and completion with accountable roles.

Prototype evidence: Five role dashboards and queues using the same saved records; one person per team. Dashboard My work/Shared workspace, scoped KPIs/charts, table search and filters, configurable columns, 8/15/30-row pagination and scoped filtered CSV export are demonstrated. Stage expansion is explicitly illustrative.

Before implementation: Approve entitlements, deputies, assignment/reassignment, SLA calendars and escalation rules.

R06 · Independent decisions and structured returns

Requirement: Tax approval, document completion and implementation are different outcomes; returns require reasons.

Prototype evidence: Separate state fields, decision controls, correction comments and sample remediation states.

Before implementation: Approve state machines, sign-off authority, deficiency acceptance/waiver and event-backed milestone history.

R07 · Safe evidence reuse

Requirement: Suggest evidence only when applicable and authorized; preserve selected evidence history.

Prototype evidence: Sample client/type/status/date eligibility and five illustrative BCTS categories.

Before implementation: Approve actual mandatory categories, alternatives, conditional rules, subtype/ownership scope, expiry and incomplete-use exceptions.

R08 · Structured Tax business processes

Requirement: Initiate BCTS and Tax Relief through forms, questions and evidence; assess country requests separately.

Prototype evidence: Individual BCTS, Denmark/Poland examples, related requests and selected-service termination.

Before implementation: Approve all field maps, BTA1–BTA9 rules, BTER format, entity/joint cases and service effective-date semantics.

R09 · Operational implementation and checking

Requirement: Record input and checking separately; final completion follows required operational work.

Prototype evidence: Marta input and Piotr check, with return-to-Tax/input paths; OBS reference capture.

Before implementation: Confirm maker-checker policy, actual OBS/iCRM writes, reconciliation and failed/partial-update recovery.

R10 · Pre account orchestration and integrations

Requirement: Retain assessment context before account availability; resume without losing lineage.

Prototype evidence: Account-created simulation, duplicate ignored, explicit freshness re-review.

Before implementation: Approve freshness threshold/change triggers, ID linkage, event schemas, idempotency, retries and manual exceptions.

R11 · Audit completion and archival

Requirement: Trace decisions and preserve completed, rejected and replaced records under governance.

Prototype evidence: Local audit events, completion library, archive read-only mode and exports.

Before implementation: Specify immutable audit, full event coverage, access, retention, legal holds, restore and disposal. Do not use dashboard stage templates as audit evidence; verify recorded events in Audit history.

R12 · Controlled replacement and change impact

Requirement: Keep original traceable and supersede only after the required acceptance state.

Prototype evidence: New ID Processing; old remains current until new Complete; rejected replacement does not supersede.

Before implementation: Decide when Tax approval is also required and how changed evidence affects open/approved cases and downstream data.

11 · Persona landing page: design and implementation notes

New navigation demonstration: the landing page adds an interactive entry point to this briefing. Sample records and deadlines are illustrative and independent of the tax-assessment application. The original guide remains available in full. Cards, counts, filters and distributions use one shared sample dataset scoped by the selected role.

Design decisionUser benefit and implementation boundary
Action-first overviewPrioritize assigned work, due dates and blockers over aggregate bank-wide volume. The reviewed application explicitly labels its aggregate as active work items: open business cases plus document reviews plus scan intake. Separate case and document-work counts clarify the components; it is not a total of unique business workflows. Completion refers to the user's work item, not necessarily the full case.
Persona-aware actionsFront Office enters via the business process catalog; Tax via review; Scan via intake; Data Input via implementation; Data Check via verification/checking. Persona switching is for demonstration only. Production identity, entitlements and record access must be enforced by authenticated APIs.
Expandable catalogKeep a workflow registry containing family ID, variant, name, domain, entry route, required capabilities, trigger type and configuration version. Add approved workflows through the registry without one navigation item per workflow. Relevant-to-role discovery is distinct from permission to start a process.
Automatic vs intentional initiationThe two document families begin through controlled intake. BCTS and the two Tax Relief paths are deliberately initiated business processes. Guide buttons explain navigation; they do not start an engine instance.
React component boundariesWorkspace shell, persona header, attention cards, work-item grid, catalog cards and detail panel are separate view responsibilities. Keep API adapters and workflow definitions separate from presentation. The HTML contains no React code. The work-item table can later use the licensed AG Grid component with server-side paging/filtering when needed.
Java / Flowable boundariesA backend worklist API should normalize task ID, case ID, family/variant, assignee, team, next action, status, due time and permitted commands. Flowable remains responsible for configured execution and task state. Server-side authorization and commands must recheck eligibility, rather than relying on hidden buttons.
Operational reliabilityAgree SLA calendars, timezone, ownership, team queues and delegation before using real metrics. APIs should distinguish loading, empty, error and stale data; provide pagination, version checks and consistent counts. The reviewed application removes historical trend, completion-rate and SLA-compliance claims. It displays configured due dates only, with no automatic waiting-period pause or synthetic scan/verification deadlines.
Accessible interactionReadable type, semantic headings and tables, visible keyboard focus, text labels with status colors, responsive panels and a keyboard-dismissable details dialog. Test the final application with assistive technology and the agreed accessibility standard.
