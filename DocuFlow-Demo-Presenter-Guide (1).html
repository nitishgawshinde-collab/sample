Payment operations: presenter and navigation reference

Aligned to docuflow-tax-assessment-reviewed(2).html, including its Payment module and fresh seeded dataset. Tax guidance is retained below. Payment data uses a separate browser storage record; switching personas shares the same cases and changes available work and actions.

Demonstration boundary: HIVE acknowledgments, OBS capture and release are simulated. Browser persona checks are not production authorization. “Completed / Archived” means a simulated release was recorded; it does not assert settlement.

Prepare the demonstration

  1. Open the exact prototype named above in a separate tab. In the Tax workspace, select Payments in the sidebar or Open payments → on the landing page/process library. Entry selects Emma Laurent.
  2. Before rehearsal, choose Scope & decisions → Reset payment demo data and confirm. This clears Payment demo edits/history and in-session attachments, while retaining Tax data. Never reset in the middle of a presentation without explaining it.
  3. Use Payment overview and search by the full case ID. Click the fund name in the matching row to open it. The ID itself is displayed under the name.
  4. Select the named persona using the top persona dropdown. Switching Payment personas keeps the open case; available actions change. Changing a role with an unsaved instruction may prompt to discard edits.
  5. Claim each required task. Team queue contains eligible unclaimed work; My tasks contains claimed work. A fresh My tasks queue can correctly be empty.

Timing: 20–25 minutes for the core sequence; add 5–10 minutes for draft, return and supervisor alternatives. Case counts and stages below apply immediately after Payment reset.

Additional flows

Draft → CSM validation → parallel controls

Emma Laurent → Payment overview → PAY-2026-2008 → Overview → Edit instruction. Keep PPMP and two lines. Use fictional sample instruction if needed. Review the demo scope/first-call/release inputs; choose Save draft or Submit to CSM validation. Submission opens Documents. Check both signature and authority confirmations, enter rationale and select Validate & start parallel controls. L1 has changed banking information, so the demo requires a new callback. This is a separate rehearsal; it is not part of the P1–P9 case.

For a new case, choose + New payment. PPMP requires at least two lines; PPSP requires exactly one. IDs are allocated from saved state, so search using the returned ID rather than promising PAY-2026-2009.

Return, recovery and terminal RED are different

An Unsuccessful payment callback moves the case to Returned to CSM. A CSM can edit and resubmit; the demo clears prior control results and capture. A checker/supervisor can choose Return to maker with a comment; this returns to Capture. Depositary Red creates recovery work. Red on PERE Ops assessment, investment callback or recovery immediately sets Stopped / Archived in the current code and records CSM notification. There is no separate CSM acknowledgment task before this terminal transition.

Empty queues or unavailable actions

Check persona → case stage → task claim → case tab. Search Payment overview when a case is absent from Team queue. Use Completed / Archived for completed records. Fresh My tasks is empty because no tasks are claimed. PAY-2026-2006 deliberately has no actionable callback while on policy hold. Do not reset to fix an expected role/stage restriction.

Questions before implementation

  • Approve callback threshold/boundary, FX source/as-of/rounding, and precedence of prior callback reuse versus amount and changed banking data.
  • Approve PERE scope/first-call source and handling of stale or unavailable indicators.
  • Decide PERE case-versus-line coverage, partial PPMP release and supervisor routing/aggregation.
  • Confirm when RED is recoverable, who acknowledges it, and whether stopping and archival are separate actions.
  • Approve real group IDs, task eligibility, canonical-person maker/checker rules, delegation and reassignment.
  • Confirm evidence matching, signed instruction/version rules, authoritative OBS confirmation, reconciliation and duplicate handling.
  • Define retention, legal holds, restart policy, SLAs and audit/access controls.

Approval requested: agree the workflow responsibilities, pilot scenarios and owners of these decisions. The prototype demonstrates behavior; it does not settle policy or certify production controls.

2 Proposed slides and speaker script

Use these headings as slides if you prepare a deck, or as spoken chapters while presenting the application. Allow about 35 minutes before questions, including dashboard explanations; optional flows can extend it to 45–60 minutes.

Slide 1 Purpose and the decision requested

Show: Dashboard → My work, Alex Morgan. Time: 1 minute.

Say: “The purpose is to replace fragmented document handling and Tax work with a shared, traceable process. We want staff to see what they own, what is missing, and what must happen next. Today I am asking whether this operating model and initial scope are right, and who will own the outstanding requirements. We are not asking you to approve unconfirmed tax rules through a screen demonstration.”

Ask: “Which operational problem should the pilot improve first: returned work, repeated evidence collection, ownership visibility, or implementation delays?”

Slide 2 Shared documents and separate outcomes

Show: Select Sophie Laurent → left sidebar Workflows & Tasks → All → enter TAX-2026-1082 in “Search client or assessment…” → click Lukas Schneider → Overview tab inside the case. Expected fresh-demo stage: Under Tax Review. This is a read-only walkthrough; do not approve or return this case during Slide 2. Time: 2 minutes.

Say: “The record separates document readiness, Tax approval, account availability, and implementation. A document can finish verification while the business assessment continues. Tax can approve an assessment before the account becomes available. Completion should tell us which outcome has actually occurred. The CRM, TAX, CDDM, and final completion tiles illustrate the proposed team milestones.”

Boundary: The team tiles currently derive from case state. A production milestone ledger with event timestamps, reversals, and historical approvals still needs design.

Ask: “Do these outcomes match your sign-off points, and what evidence proves each one?”

Slide 3 Role specific workspaces

Show: Dashboard → My work; switch through the five personas. Compare Shared workspace separately. Time: 3 minutes.

Say: “These are different views of the same saved records. Front Office sees drafts and returns, Tax sees assessments awaiting decisions, Luxembourg scanning sees paper intake, and Poland sees input or checking work. Switching persona changes dashboards, queues, counts, and actions. When Dashboard detects a different persona, it resets to My work and clears dashboard filters. Case switching retains the open case, so use Dashboard explicitly to show a different queue. It does not generate a separate client dataset. If we switch while a case is open, we stay on that case and its permitted actions change.”

Boundary: The persona selector is a demonstration control, not authentication. The shared registers remain broadly visible. Personal and team queues use one sample person per role; real assignment, deputies, desk permissions, and entitlements remain to be implemented.

Slide 3A Dashboard scope, metrics and worklist controls

Show: Dashboard → My work → Shared workspace → active worklist. Time: 4 minutes. Use Flow 0 below.

Say: “The dashboard starts with work assigned to the selected demo role. Shared workspace gives us a broader view across teams. Every KPI and chart follows that scope. Active work items is an explicit combination of business cases, document reviews and scanning intake; it is not a count of unique end-to-end workflows.”

Say while filtering: “The charts continue to summarize the selected scope. Search, status and family filters narrow this table. Export includes all matching rows across pages, not just the visible page.”

Say while expanding a row: “These are illustrative process stages and a mapping of the current state. We are not inferring that earlier tasks were completed, who performed them, or when. For recorded actions, we open the actual case and review Audit history.”

Say about dates: “Due today and Past due use existing record dates against the fixed demo date. No SLA compliance percentage is calculated. Missing deadlines show Not configured, and waiting does not automatically pause a deadline.”

Boundary: Completed and rejected cases leave active work; documents leave verification when their status no longer requires that queue. Their history remains in the existing registers. Document acceptance, Tax approval and operational completion are distinct outcomes.

Ask: “Who should see shared work, which record types should count in operational metrics, and what are the approved deadlines, calendars and pause rules?”

Slide 4 Business process library

Show: Alex → Process library. Time: 1 minute.

Say: “Users deliberately start an Account Tax Assessment, a Tax Relief request, or a service termination here. Document verification starts automatically from configured document context after intake. Future business processes can reuse the core, while retaining their own forms, routing, and decisions.”

Ask: “Which of these processes belongs in the first production release, and which countries and client types are included?”

Slide 5 BCTS checklist and evidence

Show: Alex Morgan → Workflows & Tasks → All → search TAX-2026-1081 → Amelia Bennett → BCTS checklist. Confirm Draft before following Flow A steps 1–4. Time: 5 minutes.

Say: “Front Office records identification, U.S. nationality, residency, indicia, and visa information. These five question sections are distinct from the five evidence categories. Saving answers updates the illustrative evidence requirements. We then link existing accepted records by their Document IDs. The prototype blocks submission when required evidence or confirmations are missing.”

Boundary: The exact five categories and conditional mappings have not been approved. IDEN, ADDR, NATL, and DECL are specimen codes. These examples demonstrate control behavior, not an authoritative tax checklist.

Slide 6 Tax assessment and structured correction

Show: Sophie Laurent → the submitted Amelia case → Tax & implementation; use Flow A step 5. Optionally show Isabelle’s existing return with Flow B. Time: 4 minutes.

Say: “Tax reviews the linked evidence and records its decision, rationale, and implementation instructions. Field groups refer to the supplied KS and KT references, but their allowed values and mappings need validation. A return carries a reason and correction comment back to the same request. A rejection closes the request’s active work while preserving its history.”

Ask: “Who may approve, return, reject, waive a deficiency, or revise an earlier Tax decision?”

Slide 7 Implementation and independent checking

Show: Continue Amelia through Marta Kowalska and Piotr Nowak using Flow A steps 6–7. Time: 3 minutes.

Slide 8 Multipage document review and controlled changes

6 Questions you may receive during the meeting

“Is this production ready?” “No. It validates the workflow and screen concepts. Production needs approved rules, real integrations, server-side controls, secure storage, complete audit coverage and acceptance testing.”

“Does changing persona change the client data?” “No. It changes the role’s dashboard, work queues and available actions over the same shared saved data. Production visibility will also be restricted by approved entitlements.”

“Can we reuse this in React?” “We can reuse the design language, screen structure, field definitions, sample scenarios and behavioral specifications. This HTML is not a drop-in React application. React components, Java contracts and Flowable models must be implemented and tested.”

“Are the tax rules already correct?” “Only the supplied concepts and inventory are represented. The detailed evidence, classification, country and allocation matrices need Tax SME approval. Demo values must not become production defaults.”

“Are documents actually stored in Hive or Blob?” “No. The demo stores metadata locally and temporarily holds uploaded bytes in the browser tab. Repository responsibilities and interfaces still need confirmation.”

“Can we edit or sign a real PDF here?” “We can view an uploaded PDF and record separate page-referenced notes. Editing is limited to fictional specimen copies. Legally effective signing and original PDF editing require an approved content service.”

“Does approving update OBS?” “No. The prototype records a simulated implementation and check. Production must reconcile the actual update with the approved instruction and handle failures.”

“How much faster will the process be?” “The design aims to reduce repeated entry, evidence collection and unclear handoffs. We need baseline cycle time, returns and backlog data, then a pilot to measure improvement.”

“When can we go live?” “We should estimate after the pilot scope, rule matrices, integration contracts, migration volume and platform compatibility are confirmed. The next deliverable is a scoped implementation plan with named dependencies.”

“Why does the sample not match my browser?”

“The file loads saved local records first. This guide lists the verified empty-storage snapshot. We will locate the exact ID and confirm its current stage before proceeding; we will not reset retained changes just to match a script.”

“Do expanded stages prove work was completed?”

“No. They are illustrative process stages with a current-state mapping. Use the actual record’s Audit history for recorded actions. There is no inferred completion percentage or historical actor.”

“Why are charts unchanged when I filter the worklist?”

“KPIs and charts describe My work or Shared workspace. Search and worklist filters narrow the table only; exported rows follow those table filters across all pages.”

  1. Record whether the business accepts the workflow direction, with any required changes to screens, responsibilities and milestones.
  2. Select one initial vertical slice. A candidate is individual-client BCTS from evidence selection through Tax approval, real account dependency, OBS implementation and audit. This is a proposal for approval, not an agreed scope.
  3. Assign an accountable owner and due date to every open question relevant to that slice. Record decisions with a version and approver.
